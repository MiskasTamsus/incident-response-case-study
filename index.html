Executive Summary

A backdoor built to look like nothing was there

Across roughly fifty hosted e‑commerce and WordPress sites belonging to one business network, a shared attacker toolkit was found operating at scale: hidden webshells scattered through core application folders, a database-aware redirect backdoor serving different content to search crawlers than to real visitors, and a live command-and-control channel behind it.

The obvious explanation — a vulnerability in the storefront platform everyone was running — didn’t survive contact with the evidence. What follows is the investigation that found the real common thread, the detection tooling built along the way to catch a backdoor that was actively evading signature-based scanning, and the disciplined, zero-downtime process used to remediate it cluster by cluster.

Engagement Timeline

Six phases, one campaign

Phase 1 · Discovery & Triage

Finding the first thread

Manual review of the flagship site surfaced hidden webshells and a redirect backdoor, partially already caught by the host’s own malware scanner. With roughly fifty more domains to get through, a low-cost triage trick made prioritization possible: checking a search engine’s cached favicon for a telltale swapped icon — since the live site looks completely normal to a human visitor, the backdoor only reveals itself to crawlers.

Manual forensics Cache-based triage signal
Phase 2 · Fleet-Wide Exposure

One misconfiguration, forty-three domains

A hosting panel’s per-site “SSH Access” toggle turned out to grant key-based shell access to the entire underlying hosting account — not just the one site it was opened from. That single discovery exposed 43 domains sharing one account, a massive jump over checking sites one FTP login at a time.

A server-side signature sweep across all 43 — run directly on the host, no local mirroring needed — found 35+ already carrying the toolkit: a purpose-built remote file manager hiding under an innocuous filename, paired with randomly-named webshell drops scattered through each site’s own file tree.

35+ of 43 already compromised

The signature that missed 27 out of 28

The first sweep for the backdoor’s live cloaking code used a straightforward string match — and it worked, catching one clearly-active site. But a backdoor built to evade detection doesn’t stay in one shape: a second, heavily obfuscated variant split every telltale string into individual character escapes, so no marker word ever appeared as literal text anywhere in the file.

Rather than trust the clean-looking result, the sweep was re-run with a structural fingerprint instead of a string match: a very high density of a specific PHP control-flow keyword compressed into a single minified line — a shape no ordinary application code takes. That single change surfaced 27 more actively-backdoored sites the original method had missed entirely.

The new heuristic then produced its own false positive — a legitimate, framework-generated router file that happened to share the same keyword density. Rather than patch it with a one-off exclusion (which would only cover that one filename and miss the next legitimate case), the check was tightened to the actual distinguishing trait: real generated code is normal multi-line source, even when keyword-heavy; the malicious payload is compressed to roughly one line. Re-verified clean across the fleet afterward.

FINDING 28x undercount from string-matching alone. Structural detection, then a second correction pass on the detector itself, closed the gap — and the corrected version has held up clean ever since.
Phase 3 · Root Cause, First Pass

Ruling out the obvious answer

The instinctive explanation — a bug somewhere in the e-commerce platform every affected site ran — was ruled out almost immediately: the identical toolkit, byte-for-byte, turned up on a WordPress site with no shared codebase at all. Whatever let the attacker in, it wasn’t an application-layer bug in one piece of software.

A second, genuinely separate hosting account — different login, different provider-side boundary, but built and managed by the same developer — was later found carrying the same toolkit too. That combination pointed the investigation toward a single compromised credential in the shared developer’s own tooling, not a stolen login to any one hosting panel.

Cross-platform correlation Cross-account correlation
Phase 4 · A Live-Site Scare, and a Hard Rule

The mistake that became the process

An early batch remediation attempt tripped a pre-existing, unrelated bug on one site mid-fix, forcing an immediate rollback across six domains. Five reverted perfectly — the originals had been moved aside, not deleted, before anything was replaced. The sixth hadn’t been: its original file had been overwritten directly, and the only backup on hand turned out to be incomplete.

That gap became a standing rule for everything after it: never touch a live file without moving the original aside first, and get explicit sign-off before batching changes across more than one live site at a time. Every remediation described from this point on followed it.

1 file, one-time process gap Hard rule adopted fleet-wide

Ruling out a published CVE instead of assuming it

Partway through, a credible, actively-discussed vulnerability surfaced — a pre-authentication WordPress core exploit chain with full remote code execution, publicly disclosed with proof-of-concept code. On its face it fit: it explained backdoor access to a WordPress site cleanly, and it was the kind of finding a less careful pass would have simply accepted as “solved.”

Checking it against the evidence instead of the narrative killed it in minutes: the vulnerability’s public disclosure and patch both landed well over a week after this campaign’s confirmed reconnaissance activity had already begun, and the responsible-disclosure language accompanying it made clear it hadn’t been used in the wild beforehand either. A bug that didn’t exist publicly yet cannot explain an attack that predates it.

RULED OUT Timeline analysis, not plausibility, is what actually settles an entry-vector question. The credential-compromise theory stood because this one didn’t.
Phase 5 · Disciplined Remediation

Quarantine first, verify after, cluster by cluster

Confirmed-malicious files were moved — never deleted — into a locked-down holding folder on each site before anything was replaced. Where a site’s front controller had been fully replaced by the backdoor, the malicious version was quarantined intact first, and only then swapped for a verified-clean original sourced from an already-confirmed-good install on the same fleet. Every site was checked live, before and after, on every batch.

Remediation was tiered by risk and confirmed with the client before execution: lower-risk sites (extra files only, core application untouched) went first; sites needing a core file replacement followed once the pattern held.

Quarantine, never delete Verified before & after every batch
Phase 6 · Continuous Monitoring & Hardening

Making sure it stays fixed

Hourly automated scans were stood up across all three clusters — direct server-side signature checks over an encrypted shell connection, no local mirroring required, replacing a slower file-transfer-based check that had been in place before. Bot-served doorway pages were switched from a quiet redirect to a hard “permanently gone” response, and crawler directives were checked for the same kind of cross-site sitemap poisoning already found once — and fixed everywhere else it recurred.

The monitoring earned its keep directly: a later widened check caught a site that had been marked fully remediated silently reinfected days earlier, invisible to the narrower version of the same scan the whole time. Every detection gap found this way was folded back into one shared script reused by all three clusters, so a lesson learned on one cluster is enforced on all of them from that point on — including catching and correcting its own false positives (legitimate framework test fixtures and a management tool’s own files, both individually verified benign before being excluded) rather than either suppressing them blindly or leaving noisy alerts in place. A concurrency bug that let two scans of the same cluster overlap and slow each other down was also found and fixed with a simple lock, once actually observed rather than assumed away.

289,000 requests a week that weren’t an attack

A huge, sustained volume of traffic to an admin-panel path looked, on its face, like an automated attempt to brute-force a security key — the kind of finding that demands an immediate, urgent response. Before escalating it as one, the traffic source and the code behind the path both got checked directly.

The requesting IPs resolved cleanly to a legitimate search engine’s own published crawler network — genuine, not a spoofed identity. And the path itself turned out to be unmodified platform core: every unauthenticated hit to any admin route auto-redirects to the same generic warning page by design, regardless of what’s requested. There was no key to guess in the first place — just a search crawler that had found the link and kept re-crawling it, burning bandwidth and crawl budget for nothing.

RESOLVED A one-line crawler-directive fix closed it. Verifying the source and the code first turned a false alarm into a five-minute fix instead of an incident.

A backdoor that rebuilt itself in under a minute

On one particularly stubborn WordPress site, restoring a single corrupted core file wasn’t the end of the fix — it was the trigger for something worse. Within roughly a minute of the fix landing, the site’s front controller was quietly rewritten back to the same cloaking backdoor and locked read-only, exactly as first found.

Investigating that response shape, instead of re-applying the same fix a fourth time, surfaced why: a legitimate-looking WordPress core file was silently loading a self-modifying payload disguised as an image asset on every single request. That payload had two jobs — compare the live backdoor file against its own embedded reference copy and rewrite it if different, and re-inject its own trigger into a randomly chosen core file if that trigger had been cleaned. Broadening the search from that first pair found six more injected core files and seven total copies of the same disguise script, hidden behind six different file extensions never associated with executable code. A related, unusually large single-file webshell from the same investigation turned out to have a dozen further copies scattered across the site’s own plugin directories, using deliberately malformed extensions designed to survive a casual file listing.

RESOLVED 19 hidden copies plus the corrupted core files located and restored from a known-clean reference on the same fleet. The rebuild loop stopped for good once the last trigger was gone, not before.

The tool built to manage many sites, doing exactly that

While extending the same detection sweep, a routine extension-based check flagged something unexpected: a small set of plainly legitimate-looking files, shipped with non-executable extensions by design, belonging to a self-hosted multi-site WordPress management panel installed on one domain in the fleet. Rather than dismiss it as another false positive once its own content checked out clean, the panel’s reach was traced instead — and it turned out to be actively connected, via each site’s own management-plugin credential, to essentially every WordPress site in one compromised hosting account, and independently confirmed on at least one more site in a second, genuinely separate account.

That is the first mechanism found across the entire engagement that could explain both halves of the puzzle at once: a tightly scripted, seconds-apart infection burst across dozens of domains, and a compromise that reached across hosting-account boundaries no shared login should have crossed — without requiring a separately stolen credential for every single site. The panel itself checked out as genuine, long-installed infrastructure, not something planted by the attacker; the open question is whether its own stored access credentials, not the hosting accounts’, were the thing that actually got compromised.

UNDER INVESTIGATION The strongest concrete root-cause candidate identified so far — deliberately not pursued past this point without the client directly involved, since the next step touches the panel’s own stored credentials, not just its files.
